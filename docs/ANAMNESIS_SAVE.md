# Anamnesis persistence and local recovery

Anamnesis history is stored in the existing athlete `injury_history` JSON envelope alongside other athlete metadata. No schema change or direct production-record migration is needed. The read response includes anamnesis only when the envelope contains that field.

The current client saves history using `PUT /api/atletas/:id/anamnesis` with only `history` and `baseRevision`. This transaction checks coach/organization ownership and supervision restrictions, locks the athlete, preserves all other metadata, and updates only the history and revision. Identical committed histories are safe to retry after a lost response. Stale edits return 409. Wellness, workouts and assessments are neither submitted nor rewritten, so historical readiness validation cannot block an anamnesis save. Their existing validation on `/api/salvar` remains unchanged. Older clients retain the full-snapshot persistence path.

Omitted history from an older client preserves the stored array under the existing athlete row lock. Explicit `[]` remains an intentional empty history. Legacy database absence must not be converted to an empty array: the client merges retain tablet-only history when the remote property is absent, while explicit remote arrays remain authoritative.

The modal awaits an explicit matching server receipt and displays success only afterward. Failures retain the form/local athlete cache, with a dedicated pending-history copy in scoped local storage. Retries of an unconfirmed form use the same record ID. The history tab offers `Salvar histórico no banco` to submit a legacy local history through the dedicated authenticated endpoint. The button does not recreate answers or recover cache which has already been erased. Recovery still requires using the original device/browser where a local copy may exist.

Additional regression validation exercised the complete HTTP/client/storage path with a historical readiness score of 120: `/api/salvar` validation still rejects it while the isolated anamnesis save succeeds, preserves those historical data unchanged, and can be read from the athlete envelope. Tests cover idempotency, archived/foreign athletes, stale writes, read-only supervision, commit rollback, restricted payload fields and incomplete acknowledgments.

Validation used synthetic data: 24 focused tests including PostgreSQL-compatible storage round-trip, omitted-history preservation, invalid/cross-athlete rejection and cache merge behavior. Chromium checks verified rejected saves, stable retry IDs, acknowledgment-driven success, history confirmation and resetting the confirmation label on a new form. Type checks and the production build passed. No real athlete's answers were created or altered during verification.
